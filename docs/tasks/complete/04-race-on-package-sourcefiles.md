# Гонка при записи в package-level `sourceFiles` и неполный подсчёт `len`

**Приоритет:** высокий
**Файлы:** `cmd/cmd_find.go`
**Категория:** race condition / корректность индекса

## Проблема

1. **Гонка записи в мапу.** `fillSourceFiles` (`cmd/cmd_find.go:138-156`) пишет

   `sourceFiles[...]` из отдельной горутины, читающей `filesChan`, без мьютекса.

   Одновременный доступ к пакетной мапе из нескольких горутин — **data race**.

2. **Неполный `len(sourceFiles)`.** `run` (`cmd/cmd_find.go:78`) сразу читает

   `len(sourceFiles)` сразу после `fillSourceFiles`, но горутина-потребитель канала

   записывает в мапу асинхронно без `WaitGroup`. Задержка записи приводит к тому, что

   `len(sourceFiles)` может быть **меньше реального числа файлов**, а последующая

   итерация target может начаться до завершения индексации source.

3. **Накопление между запусками.** `sourceFiles` — пакетная переменная

   (`cmd/cmd_find.go:42`), не сбрасывается между вызовами `run`. При повторном вызове в

   одной программе (режим библиотеки) накапливаются записи прошлых запусков.

## Ожидаемое поведение / решение

1. Синхронизировать запись в `sourceFiles` (мьютекс или защищённая структура).
2. Дожимать горутину-потребитель (`WaitGroup`) перед возвратом из `fillSourceFiles` и

   перед чтением `len(sourceFiles)` и началом итерации target.
3. Сбрасывать `sourceFiles` в начале `fillSourceFiles` (или самого `run`).

## Acceptance criteria

- `go test -race`/`go run -race` не фиксирует data race при параллельном запуске.
- `len(sourceFiles)` корректен к моменту начала обхода target.
- Повторный запуск в одной программе не содержит записей прошлых запусков.
